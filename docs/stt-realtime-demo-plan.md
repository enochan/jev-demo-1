# デモ企画：STT × リアルタイム判定 — 価値のある場面の探索

会話を音声認識（STT）でその場で文字に起こし、発話が終わるたびに Jev で判定し直す。既存の「リアルタイム：面談メモ」（キーボード入力のたびに判定）の入力を、声に置き換える企画である。

このメモは「どこで使えば価値があるか」の探索が主目的で、実装方針は後半に短くまとめる。

---

## 1. 前提：STT × 判定が効く条件

文字起こし自体は既にありふれている。会話が終わってから全文を LLM に読ませれば、要約も判定もできる。それでも **会話中に** 判定する意味があるのは、次の条件がそろう場面に限られる。

| 条件 | 中身 | 当てはまらないと |
|---|---|---|
| **会話中に行動が変わる** | 判定結果を見て、その場で聞き足す・止める・人を呼ぶ | 終わってから一括判定すればよい（既存の支援記録チェックと同じ） |
| **書く・画面を見る余裕がない** | 相手の顔を見て話す、電話で手がふさがる、活動中で両手が使えない | キーボード入力版で足りる |
| **見逃しのコストが高い** | 聞き漏れで再訪問が要る、危機のサインを流すと取り返しがつかない | 便利なだけで導入の動機が弱い |
| **判断を固定の選択肢で書ける** | 「聞けたか／まだか」「危機のサインがあるか」「次の行動は A〜D のどれか」 | 要約や助言文が欲しいなら LLM の仕事 |

Jev がこの組み合わせに向く理由は2つある。

- **速い**：STT は発話の切れ目ごとに確定文を返す。1回 0.2 秒前後で返る判定なら、話者が次の文を話し始める前に表示が更新される。LLM で毎回 2〜5 秒かかると、表示が会話に追いつかない。
- **毎回全文を読み直しても安い**：出力トークンは無料で、入力トークンだけが課金される。30分の面談（約9,000字、数千トークン）を発話ごと（約200回）に全文で判定し直しても、入力は合計で百万トークン前後になる。リーディングリストにある Cloudflare 経由の単価（入力 $0.042/1M）なら数セントで済む（単価は利用時に要確認）。

## 2. 場面の候補（障害福祉の業務から）

既存デモと同じく障害福祉の現場を題材にする。「支援系／運営系／開発系」に加えて、当事者が使う場面も入れた。

### A. 相談電話の受付：危機のサインと聞き取り漏れ（運営系）

- **場面**：相談支援事業所や事業所の代表電話。家族・本人・関係機関から電話が入る
- **判定すること**
  - 危機のサイン（希死念慮、虐待・ネグレクトの疑い、急病）→ Noul
  - 聞き取り項目（名前・連絡先・利用中のサービス・困りごと・緊急度）が聞けたか → 項目ごとの Noul
  - 次の対応（折り返し／担当者へ転送／その場で管理者に代わる／関係機関へ連絡）→ Choice
- **なぜ会話中か**：危機対応は電話を切る前に動く必要がある。聞き漏れは折り返しの手間になり、相手が連絡のつきにくい人だとそのまま途切れる
- **見せ方**：受付者の画面には「まだ聞いていない項目」だけを出し、危機のサインは管理者の画面にも同時に出す（受付者を急かさない）

### B. 初回面談・アセスメントの聞き取りチェック（支援系）

- **場面**：サービス利用前の初回面談、計画相談のアセスメント
- **判定すること**：アセスメント項目（障害特性・服薬と通院・家族の状況・本人の希望・緊急連絡先・利用中の他サービスなど）が話題に出たか。項目は事業所ごとに違うので、質問定義の JSON を書き換えるだけで差し替えられる点が見せどころになる
- **なぜ会話中か**：面談の最後に「あと聞いていないのは2項目」と分かれば、その場で聞ける。後で気づくと電話か再面談になる
- **注意**：本人の前で画面をのぞき込むと面談の雰囲気を壊す。タブレットを手元に置き、点灯の変化だけをちらっと見る程度の UI にする

### C. 就労定着支援の三者面談：合理的配慮の確認（支援系）

- **場面**：本人・企業担当者・支援員の三者面談
- **判定すること**：合意済みの配慮（例：指示はメモで、休憩の取り方）が守られているかを示す発言があるか、業務量の変化、本人が言いにくそうにしている様子、次の行動（様子見／本人と再面談／業務調整を提案）
- **なぜ会話中か**：企業担当者がいるうちに配慮の話を持ち出せるかどうかで、調整の速さが変わる。後日あらためて企業に連絡するのは心理的なハードルが高い
- **既存デモとの関係**：「面談メモ」デモの質問をほぼそのまま使える。入力が声になるだけなので、比較して見せやすい

### D. 個別支援計画の担当者会議・モニタリング：運営指導で問われる手続き（運営系）

- **場面**：サービス担当者会議、個別支援計画の説明・同意、モニタリング面談
- **判定すること**：本人（家族）の意向を確認したか、計画の内容を説明したか、同意を得たか、次回モニタリングの時期を決めたか
- **なぜ会話中か**：運営指導（実地指導）で記録の不備を指摘されると減算につながる。会議が終わる前に「同意の確認がまだ」と分かれば、その場で済む
- **注意**：判定は「手続きが会話に出たか」の確認までにとどめる。同意の有効性そのものは人が判断する

### E. 活動中のハンズフリー報告：ヒヤリハットの一次判定（支援系）

- **場面**：放課後等デイサービスの外出・活動中。職員がスマホに向かって「今、○○くんが道路に飛び出しそうになった」と話す
- **判定すること**：事故／ヒヤリハット／報告不要の区分、保護者連絡の要否、管理者への即時連絡の要否
- **なぜ会話中か**：両手がふさがっていて書けない。記憶が新しいうちに口頭で残し、報告書が要るものだけ後で清書する
- **既存デモとの関係**：「支援記録チェック」の質問を流用できる。厳密には会話ではなく独り言だが、STT の価値（書けない）がいちばん分かりやすい

### F. 聴覚障害のある人への「自分宛てか」の通知（当事者向け）

- **場面**：聴覚障害のある社員・利用者が職場や事業所にいる。周囲の会話や館内放送を字幕にする
- **判定すること**：自分の名前・自分への呼びかけか、指示や依頼を含むか、緊急の案内（避難・急病）か
- **なぜ会話中か**：字幕を常に読み続けるのは負担が大きい。全部を読ませるのではなく、自分に関係する発話だけを振動や色で知らせる。文字起こしだけでは足りず、判定があって初めて成り立つ
- **注意**：周囲の人の発話を記録するので、職場での合意が要る。音声は保存しない設計にする

### G. 就職面接の練習：回答のフィードバック（支援系・当事者向け）

- **場面**：就労移行支援の模擬面接。利用者が面接官役（職員や AI）の質問に声で答える
- **判定すること**：質問に答えているか、配慮してほしいことを具体的に伝えられたか、否定的な言い回しが多すぎないか、回答の長さ（長すぎ・短すぎ）
- **なぜ会話中か**：1問ごとにすぐ結果が出ると、言い直しを何度も試せる。後でまとめて講評するより練習の回数が増える
- **デモ向きな点**：本人が自分の練習のために使うので、監視の懸念がいちばん少ない。会場の参加者がその場で答えて試せる

### H. 新人支援員の相談対応ロールプレイ（研修）

- **場面**：新人研修で、先輩が利用者・家族役を演じる
- **判定すること**：開かれた質問を使えているか、相手の話を遮っていないか、本人の言葉を言い換えて確認しているか、危機のサインに反応できたか
- **なぜ会話中か**：ロールプレイの後に録音を聞き返す時間は取りにくい。終わった直後に、どこで何が起きたかを時系列で見られる
- **注意**：本番の業務で職員の発話を採点すると、監視と受け取られやすい。研修の場に限るのが無難

### I. 音声対話 AI の入力ガードレール（開発系）

- **場面**：電話や音声で使う相談 AI（就労相談ボットの音声版など）
- **判定すること**：既存の「AIチャットのガードレール」と同じ（危機対応・インジェクション・個人情報・医療判断）
- **なぜ会話中か**：音声対話は応答の遅れがそのまま沈黙になる。LLM の前に 0.2 秒で判定を挟めるかどうかが、音声で使えるかの分かれ目になる
- **既存デモとの関係**：入力を声にするだけで、質問定義はそのまま使える

## 3. 候補の比較

◎＝強く当てはまる、○＝当てはまる、△＝弱い。「監視・同意の懸念」は ◎ が懸念が少ない側。

| 場面 | 会話中に行動が変わる | 書けない・見られない | 見逃しのコスト | 監視・同意の懸念 | 会場で再現しやすい |
|---|---|---|---|---|---|
| A. 相談電話の受付 | ◎ | ◎ | ◎ | ○ | ○（台本） |
| B. 初回面談の聞き取り | ◎ | ○ | ○ | ○ | ○（台本） |
| C. 三者面談の配慮確認 | ○ | ○ | ○ | ○ | ○（台本） |
| D. 担当者会議の手続き | ○ | △ | ○ | ○ | △ |
| E. ハンズフリー報告 | △ | ◎ | ○ | ◎ | ◎ |
| F. 「自分宛てか」の通知 | ◎ | ◎ | ○ | △ | ○ |
| G. 面接練習 | ○ | ○ | △ | ◎ | ◎（参加型） |
| H. 研修ロールプレイ | △ | ○ | △ | ○ | ◎ |
| I. 音声 AI のガードレール | ◎ | — | ◎ | ○ | ○ |

**向かない場面**も挙げておく。

- **議事録の要約・決定事項の抽出**：文章を書く仕事なので LLM が向く。会議後に一括でよい
- **本番業務での職員の発話の採点**：言葉づかいの判定（虐待防止）などは価値があっても、常時の監視と受け取られると現場の信頼を失う。研修（H）か本人の同意がある範囲に限る
- **診断的な判断**：「この発言からうつ病か」のような判断はさせない。リーディングリストの医療ベンチマークでも、「分からない」を選ぶべき場面でほとんど選ばなかったと報告されている

## 4. 勉強会で見せるなら

### 推しの組み合わせ

1. **A. 相談電話の受付**（主役）：価値がいちばん説明しやすい。職員2人が台本で電話役を演じ、途中で危機のサインが出る流れにする。「まだ聞いていない項目」が会話の進行とともに消えていき、危機のサインで管理者の欄が点灯する
2. **G. 面接練習**（参加型）：会場の誰かに模擬面接の質問へ答えてもらい、その場で判定が出る。監視の懸念が少なく、盛り上がりやすい
3. 時間があれば **F. 「自分宛てか」の通知**：当事者が使う場面を1つ入れると、「業務効率化だけの道具ではない」というメッセージになる

### 見せたいポイント

- **入力が声でも、質問定義は同じ JSON**：既存の面談メモの質問を流用したシナリオを1つ入れ、キーボード版との違いが入力だけであることを見せる
- **発話のたびに全文を判定し直しても速い・安い**：画面に「発話数・判定回数・中央値レイテンシ・累計入力トークン」を出す
- **「聞けた」は消えない、「リスク」は上下する**：聞き取り項目は一度点灯したら消さない（最大値を保持する）。危機・リスクのスコアは会話の流れで上下する様子を折れ線で見せる
- **認識ミスへの強さ**：「服薬」が「福薬」になるなど、STT の誤認識を混ぜた台本でも判定が崩れないかを見せる（崩れるなら、それも正直に見せる）

## 5. 実装の方針（既存デモへの追加）

既存の `realtime` モードに乗せる。サーバー側の変更はほぼ要らない。

| 項目 | 方針 |
|---|---|
| STT | まずはブラウザの Web Speech API（`webkitSpeechRecognition`、`lang = "ja-JP"`、`interimResults = true`）。追加の依存なしで動く。Chrome / Edge のみで、音声は Google のサーバーに送られるため、ダミーの会話に限る |
| 判定のタイミング | 確定した発話（`isFinal`）を `liveText` に追記して `scheduleLive()` を呼ぶ。途中結果は灰色で表示するだけで判定しない。古い応答を捨てる仕組み（`liveSeq`）は既存のものが使える |
| 話者の区別 | Web Speech API は話者分離ができない。「支援員／相手」の切り替えボタン（押している間だけ話す方式）で行頭に話者名を付ける |
| マイクがない・会場がうるさいとき | 既存の「会話を再生」（`script`）で同じ流れを再生できるようにしておく。オフライン時のキャッシュ再生も既存の仕組みのまま |
| シナリオの追加 | `scenarios.json` に `realtime` のシナリオを足し、`"stt": true` でマイクボタンを出す。A・G（・F）の台本と質問を書く |
| 表示 | 聞き取り項目は最大値を保持してチェックリスト表示、リスク系は直近 N 回の推移を表示 |

### 本番で使うなら（デモの範囲外）

- **STT の選択肢**：日本語の精度と、音声をどこに送るかで選ぶ。クラウドの STT（Google / Azure / OpenAI など）、日本語や医療・介護の用語に強い国内製品、手元で動かす Whisper 系（faster-whisper など）。要配慮個人情報を含む会話は、保存しない設定か手元で動くものを優先する
- **同意と保存**：録音・文字起こしをすることを相手に伝え、同意を得る。音声は保存せず、文字起こしも判定後に破棄する設計を基本にする
- **しきい値**：危機のサインは見逃しのコストが高いので、しきい値を低めにして人が確認する前提にする（既存デモのしきい値スライダーの考え方と同じ）
- **長い会話**：Jev のコンテキストは 32k トークン。1時間を超える会議では、直近の数分＋それまでの判定結果を state に入れるなど、窓を切る工夫が要る

## 6. 現場に聞いて確かめたいこと

企画を絞る前に、現場の職員に次を聞きたい。

1. 電話や面談で「聞き忘れて、後で連絡し直した」ことはどのくらいあるか。どの項目が多いか
2. 面談中に手元の画面やタブレットを見ることに、抵抗はあるか
3. 危機のサインを受付者以外（管理者）にも同時に知らせることを、受付者はどう感じるか
4. 録音・文字起こしについて、利用者や家族から同意を得るのは現実的か
5. 聴覚障害のある利用者・職員から、字幕や通知について要望を聞いたことはあるか

## 次の一歩

3. 台本の再生とマイク入力の両方で、判定の流れが意図どおりになるか LIVE で確かめ、キャッシュを作っておく
