Jevとは

文章を書かない。判断だけを返すモデル。

  • TypeSafe AI が 2026/09/15 に公開した decision model（判断モデル）。同社は「System One」モデルと呼んでいる
  • 入力は state（テキストでもJSONでもよい）と、名前付きの 型付きの質問の集合
  • 全部の質問に 1回の呼び出しで並列に答え、すべての答えに 確率が付く
  • 公表値：70–500ms、入力 $0.042 / 1Mトークン、出力は無料

※ 性能・価格はベンダー公表値。独立したベンチマークはまだ少ない

LLM と何が違うか

LLM（Claude / GPT など）Jev
出力自由文。JSON形式は「お願い」して出してもらう型付きの答えのみ（選択肢・スコア・Yes確率）
信頼度自己申告の「自信」は当てにならない確率が出る。確率が当たるように学習（RLCD）
複数の判断プロンプトを分ける／まとめて出させるN問を1回の呼び出しで並列に処理
速度・コスト秒単位・出力課金数百ms・出力無料
得意生成・要約・推論・対話分類・ルーティング・採点・ゲート判定

→ 置き換えではなく役割分担。「if文の条件をAIに書いてもらう」イメージ

3つの質問型

Choice

候補から1つ選ぶ

→ choice / confidence / 各候補の probabilities

例：5領域のどれ？　どの担当に回す？

Score

順序付きの段階（ルーブリック）で採点

→ 期待スコア（小数）/ confidence / 段階ごとの確率

例：本人の状態 0〜3、記録の具体性

Noul

Yes/No の確率

→ noul = p(yes)（0〜1）

例：ヒヤリハットに該当？　苦情を含む？

instructions / criteria は 文字列でもJSONでも書ける。学習データは不要で、質問を書き足すだけで判断項目が増える

コードはこれだけ（Python SDK: typesafe-sdk）

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

with TypeSafeClient() as client:            # TYPESAFE_API_KEY を読む / モデル既定値は jev-latest
    res = client.system_one(
        state={"支援記録": text, "事業所種別": "放課後等デイサービス"},
        questions={
            "domain":   Choice(instructions="5領域のどれに関係？",
                              criteria={"健康・生活": "…", "運動・感覚": "…", ...}),
            "incident": Noul(instructions="事故・ヒヤリハットの記載がある？"),
            "condition": Score(instructions="本人の状態は？",
                              criteria=["安定", "やや不安定", "個別対応が必要", "強い不調"]),
        },
    )

res.choices["domain"].choice, res.choices["domain"].confidence
res.nouls["incident"].noul         # 0.95 → if 文にそのまま使える
res.scores["condition"].score      # 確率で重み付けした期待値（例：1.7）

REST：POST https://api.typesafe.ai/v1/systemone（Bearer認証）／ 非同期クライアント AsyncTypeSafeClient あり

本当にうれしいのは「確率」

AIに任せる範囲を、
しきい値というつまみ1つで決められる

  • 確率が高いものは自動で処理し、迷っているものだけ人が見る（human-in-the-loop を設計できる）
  • 「見逃しを0にしたい」「人の確認件数を半分にしたい」を数字で話せる
  • LLMでは「たぶん合ってる」を定量化しにくかった

デモ① 支援記録チェック 支援系

放課後等デイサービスの日々の支援記録（ダミー16件）に、6問を1回で投げる

  • 5領域の分類（Choice）
  • 事故・ヒヤリハット（Noul）
  • 虐待のサイン／権利擁護の観点（Noul）
  • 保護者への共有事項（Noul）
  • 本人の状態・記録の具体性（Score）

見てほしいところ

  • 16件 × 6問 が 1秒かからずに終わる
  • しきい値を動かすと
    管理者が読む件数と見逃しが連動する
  • 「今日は楽しそうだった」だけの記録は
    記録の具体性 0（監査対策にも使える）
  • その場で記録を打ち込んで判定

デモ② 問い合わせトリアージ 運営系

Webフォームに届く問い合わせ（ダミー14件）を一括判定

  • サービス：児童発達支援／放デイ／就労移行／定着／その他
  • 送り主：保護者／本人／相談支援専門員・行政／企業
  • 見学希望・受給者証の質問・苦情（Noul）
  • 緊急度（Score）

見てほしいところ

  • confidence のしきい値で
    自動振り分け率 と 自動分の正解率のトレードオフ
  • 曖昧な問い合わせ（お礼だけ、年齢が書いていない等）は confidence が下がって人に回る
  • 質問JSONをその場で書き換えて再実行（例：「SNS経由か？」を追加）

障害福祉で使うときの注意

データ

  • 支援記録は要配慮個人情報の塊。外部API（米国企業）に送る前提で、同意・匿名化・契約・データ保持を確認する
  • 今日のデモはすべてダミー

判断の責任

  • 虐待の疑い・事故報告は法令上の義務。AIは「見落とさないための補助」であって、判定はしない
  • 見逃しと過検知はコストが非対称 → しきい値は安全側に

精度

  • 確率がどれだけ当たっているかは自分たちのデータで検証してから使う
  • 正解ラベル付きのサンプルを少数でも作るのが第一歩

現場の受け止め

  • 「AIに見張られている」ではなく
    「書いた記録が誰かに届く」体験として設計する

ブレスト：判断を棚卸しする

あなたの業務で、
選ぶ / 点をつける / Yes・Noを決める を
毎日たくさんやっているのはどこ？

① 件数

1日・1か月で何件？
誰が何分かけている？

② 間違えたときのコスト

見逃すと何が起きる？
過検知だと何が起きる？

③ 判断材料

テキスト／フォームとして
すでにデータになっている？

件数が多く、データがあり、AIを外したときのコストが許容できるもの → まず試す候補

ブレストの種

支援系

  • 連絡帳・支援記録 → 保護者に共有すべき事項の抜け漏れチェック
  • モニタリング記録 → 個別支援計画の目標ごとの達成度スコア
  • 就労移行の日報 → 体調悪化・通所中断のサインを早めに検知
  • 定着支援の面談記録 → 離職リスクのスコア
  • ケース記録 → 加算の算定要件を満たす記載があるか

運営系

  • 問い合わせ・見学申込の振り分け、折り返しの優先度付け
  • 苦情・ヒヤリハット報告の分類と傾向分析
  • 求人応募者の書類一次チェック（※バイアスに注意）
  • 請求前チェック：実績記録と計画の整合性
  • 社内ヘルプデスク・稟議の規程チェック
  • LLMで作った文書の品質ゲート（LLM × Jev）

export TYPESAFE_API_KEY=...            # console.typesafe.ai で発行

# キーがない／会場のネットワークが不安定な場合
