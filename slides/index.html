Jevとは

文章を書かず、判断だけを返すモデル。

  • TypeSafe AI が 2026/09/15 に公開した decision model（判断モデル）。同社は「System One」モデルと呼んでいる
  • 入力は state（テキストでもJSONでもよい）と、名前付きの 型付きの質問の集合
  • すべての質問に 1回の呼び出しで並列に回答し、各回答に 確率が付く
  • 公表値：70–500ms、入力 $0.042 / 1Mトークン、出力は無料

※ 性能・価格はベンダー公表値。第三者によるベンチマークはまだ少ない

社内でも関心が高まっている

  • 公開直後から、社内のエンジニアを中心に情報共有が進んでいる
  • 共通した理解：「判断するAI」「速い・安い」「巨大なSwitch文」
  • 公式のウェイトリストのほか、OpenRouter・Cloudflare からも利用できる

すでに出ている当てはめ先

  • 支援計画・教材：教材推薦の適合判定、支援内容の関連性判定、QAでの評価判定
  • AIチャット：LLMで行っている入出力チェック（ガードレール）の置き換え
  • 求人マッチング：求職者 × 求人の即時ランキング

今日は「アイデア」から「触ってみた」に一歩進める回

LLM と何が違うか

LLM（Claude / GPT など）Jev
出力自由文。JSON形式はプロンプトで明示的に指定して出力させる型付きの答えのみ（選択肢・スコア・Yes確率）
信頼度自己申告の「自信」は当てにならない確率が出る。確率が当たるように学習（RLCD）
複数の判断プロンプトを分ける／まとめて出させるN問を1回の呼び出しで並列に処理
速度・コスト秒単位・出力課金数百ms・出力無料
得意生成・要約・推論・対話分類・ルーティング・採点・ゲート判定

→ 置き換えではなく役割分担。「if文の条件判定をAIに任せる」イメージ

3つの質問型

Choice

候補から1つ選ぶ

→ choice / confidence / 各候補の probabilities

例：5領域のどれ？　どの担当に回す？

Score

順序付きの段階（ルーブリック）で採点

→ 期待スコア（小数）/ confidence / 段階ごとの確率

例：利用者の状態 0〜3、記録の具体性

Noul

Yes/No の確率

→ noul = p(yes)（0〜1）

例：ヒヤリハットに該当？　苦情を含む？

instructions / criteria は 文字列でもJSONでも書ける。学習データは不要で、質問を書き足すだけで判断項目を増やせる

判断に「確率」が付く利点

AIに任せる範囲を、
しきい値というパラメータ1つで調整できる

  • 確率が高いものは自動で処理し、判断が分かれるものだけ人が確認する（human-in-the-loop を設計できる）
  • 「見逃しを0にしたい」「人の確認件数を半分にしたい」を数字で検討できる
  • LLMでは「たぶん合ってる」を定量化しにくかった

デモ① 支援記録チェック 支援系

放課後等デイサービスの日々の支援記録（ダミー16件）に、6問を1回で送る

  • 5領域の分類（Choice）
  • 事故・ヒヤリハット（Noul）
  • 虐待のサイン／権利擁護の観点（Noul）
  • 保護者への共有事項（Noul）
  • 利用者の状態・記録の具体性（Score）

確認ポイント

  • 16件 × 6問 が 1秒かからずに終わる
  • しきい値を動かすと
    管理者が確認する件数と見逃しが連動する
  • 「今日は楽しそうだった」だけの記録は
    記録の具体性 0（監査対策にも活用できる）
  • その場で記録を入力して判定

デモ② 問い合わせトリアージ 運営系

Webフォームに届く問い合わせ（ダミー14件）を一括判定

  • サービス：児童発達支援／放デイ／就労移行／定着／その他
  • 送り主：保護者／本人／相談支援専門員・行政／企業
  • 見学希望・受給者証の質問・苦情（Noul）
  • 緊急度（Score）

確認ポイント

  • confidence のしきい値で
    自動振り分け率 と 自動処理分の正解率のトレードオフを調整
  • 曖昧な問い合わせ（お礼のみ、年齢未記載など）は confidence が下がって人による対応へ回る
  • 質問JSONをその場で書き換えて再実行（例：「SNS経由か？」を追加）

デモ③ AIチャットのガードレール 開発系

就職・就労相談チャットへの入力（ダミー12件）を、LLM に渡す前にチェックする

  • 危機対応（自傷・希死念慮）→ 人につなぐ
  • プロンプトインジェクション
  • 個人情報（氏名・電話・手帳番号）
  • 医療判断の要求（服薬量・診断）
  • 対象内／対象外（Choice）、困り度（Score）

想定する構成

  • LLMによる入出力チェックは、前後それぞれ秒単位の待ち時間が発生しやすい
  • Jev：4種類のチェックを1回の呼び出しで処理
  • 回答生成と安全ガードを分ける構成
  • 「消えてしまいたい」のような遠回しな表現を拾えるか？ → しきい値をどこに設定するか？

デモ④〜⑦ 判断の型を広げる 応用

④⑤ ランキング

  • 求職者 × 求人10件、子どもの支援目標 × 教材10件
  • 候補ごとに Noul を1問ずつ作成し、10問を1回の呼び出しで判定して確率順に並べる
  • プロフィールを切り替えると順位が入れ替わる（▲▼で変動を表示）

⑥ リアルタイム判定

  • 就労定着支援の面談メモを、入力が止まるたびに再判定
  • 会話が進むにつれて、体調・業務量・人間関係・合理的配慮のネックが順に点灯
  • 応答速度が前提となるユースケース

⑦ 構造化データ

  • 就労移行支援の日報10日分をJSONのまま state に渡す
  • 通所中断のリスクと、今週中の個別面談の要否を判定
  • 文章だけでなく、記録システムのデータも判定対象になる

確認ポイント

  • 学習なしで、質問の定義を変えるだけで用途が変わる
  • 1件×多問（①〜③）、多候補×1問（④⑤）、連続入力（⑥）、JSON入力（⑦）

社内で出ている慎重論への考え方

懸念考え方
精度は？ 偽陽性・偽陰性が気になる確率が返るため、しきい値で FP / FN のどちらを許容するかを設計できる。
正解付きのサンプルで、デモのようにトレードオフの曲線を描いてから決める
「なぜマッチか」の説明が価値では？2段構成：Jev で速く安く絞り込み・並べ替えを行い、上位のみ LLM で説明文を生成する
「ハルシネーションしない」は本当？自由文を出力しないだけで、モデルが判断を誤ることはある。出力の形式が崩れないことと、判断内容の正しさは別
中身がよく分からない（巨大Switch文？）実用上はそれで十分。「if 文の条件判定を自然言語で記述できる仕組み」と捉えて使う

障害福祉で使うときの注意点

  • データ管理
    • 支援記録は要配慮個人情報に該当する。外部API（米国企業）へ送信する前提として、本人の同意、匿名化、契約内容、データ保持方針を確認する
    • 本勉強会のデモデータはすべて架空のダミー
  • 判断の責任
    • 虐待の疑いや事故報告は法令上の義務。AIは「職員が見落とさないための補助」であり、最終判定は人が担う
    • 見逃しと過検知は発生時の影響が非対称（重大事故の見逃しリスクが高い） → しきい値は安全側に設定する
  • 精度検証
    • 出力される確率がどの程度実際と一致しているかは、自組織のデータで検証してから導入する
    • 正解ラベル付きのサンプルを少数でも作成して評価するのが第一歩
  • 現場での受容性
    • 「AIに監視されている」という心理的負担を避け、「書いた支援記録が適切に共有・活用される」体験として設計する

ブレスト：判断を棚卸しする

事業・プロダクト・サービスの中で、
「選ぶ」「点をつける」「Yes/Noを決める」 が
頻繁に発生している業務はどこか？

① 発生件数

1日・1か月で何回起きるか？
現在誰が（人または既存システムが）判断しているか？

② 誤判定時の影響

見逃すとどのような事態が起きるか？
過検知だと運用上どう負担になるか？

③ 判断材料のデータ化

テキストや入力フォームとして、
すでに構造化・データ化されているか？

観点例：利用者・家族の体験／支援品質／現場の業務負荷／事業運営・収益性／プロダクト機能・開発
件数が多く、判断材料がデータとして揃っており、誤判定時の影響を運用で許容できるものから着手する

ブレストの候補例

支援系

  • 連絡帳・支援記録 → 保護者へ共有すべき重要事項の記載漏れ検知
  • モニタリング記録 → 個別支援計画の目標ごとの進捗・達成度スコア算出
  • 就労移行の日報 → 体調悪化や通所中断のサインの早期検知
  • 定着支援の面談記録 → 離職リスクのスコアリング
  • ケース記録 → 加算の算定要件を満たす記載の有無チェック

運営系

  • 問い合わせ・見学申込の一次振り分けと、折り返し対応の優先度判定
  • 苦情・ヒヤリハット報告の自動分類と傾向分析
  • 求人応募書類の一次要件チェック（※バイアスへの配慮が必要）
  • 請求前チェック：実績記録票と支援計画の整合性確認
  • 社内ヘルプデスク・稟議申請における規程遵守チェック
  • LLM生成文書の品質検査ゲート（LLMとJevの組み合わせ）

開発系（社内で既出）：ツール呼び出し結果の圧縮／長文の対話内容の判定（grill-jev）／軽量・高速な静的検査／QA時の評価判定を置き換えたテストコスト削減
