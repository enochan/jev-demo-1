Jevとは

文章を書かない。判断だけを返すモデル。

  • TypeSafe AI が 2026/09/15 に公開した decision model（判断モデル）。同社は「System One」モデルと呼んでいる
  • 入力は state（テキストでもJSONでもよい）と、名前付きの 型付きの質問の集合
  • 全部の質問に 1回の呼び出しで並列に答え、すべての答えに 確率が付く
  • 公表値：70–500ms、入力 $0.042 / 1Mトークン、出力は無料

※ 性能・価格はベンダー公表値。独立したベンチマークはまだ少ない

社内でももう話題になっている（公開チャンネル・9/16〜19）

  • 9/16 公式ブログが共有される → 9/18 には「はてブがJevだらけ」
  • まず個人timesと事業部チャンネルで広がった（横断のAIチャンネルにはまだあまり出てこない）
  • 共通した理解：「判断するAI」「速い・安い」「巨大なSwitch文」
  • ウェイトリストは1日ほどで通過したという報告。OpenRouter・Cloudflare からも使える

すでに出ている当てはめ先

  • IEP：教材推薦の「良さそう判定」、手立て・見立ての関連性、ガードレール、QAの LLM-as-a-Judge
  • 仕事ナビ：Haiku で前後チェックしている自前ガードレール（前後 1秒ずつ）の置き換え
  • スナビジョン：求職者 × 求人の即時ランキング

LLM と何が違うか

LLM（Claude / GPT など）Jev
出力自由文。JSON形式は「お願い」して出してもらう型付きの答えのみ（選択肢・スコア・Yes確率）
信頼度自己申告の「自信」は当てにならない確率が出る。確率が当たるように学習（RLCD）
複数の判断プロンプトを分ける／まとめて出させるN問を1回の呼び出しで並列に処理
速度・コスト秒単位・出力課金数百ms・出力無料
得意生成・要約・推論・対話分類・ルーティング・採点・ゲート判定

→ 置き換えではなく役割分担。「if文の条件をAIに書いてもらう」イメージ

3つの質問型

Choice

候補から1つ選ぶ

→ choice / confidence / 各候補の probabilities

例：5領域のどれ？　どの担当に回す？

Score

順序付きの段階（ルーブリック）で採点

→ 期待スコア（小数）/ confidence / 段階ごとの確率

例：本人の状態 0〜3、記録の具体性

Noul

Yes/No の確率

→ noul = p(yes)（0〜1）

例：ヒヤリハットに該当？　苦情を含む？

instructions / criteria は 文字列でもJSONでも書ける。学習データは不要で、質問を書き足すだけで判断項目が増える

本当にうれしいのは「確率」

AIに任せる範囲を、
しきい値というつまみ1つで決められる

  • 確率が高いものは自動で処理し、迷っているものだけ人が見る（human-in-the-loop を設計できる）
  • 「見逃しを0にしたい」「人の確認件数を半分にしたい」を数字で話せる
  • LLMでは「たぶん合ってる」を定量化しにくかった

デモ① 支援記録チェック 支援系

放課後等デイサービスの日々の支援記録（ダミー16件）に、6問を1回で投げる

  • 5領域の分類（Choice）
  • 事故・ヒヤリハット（Noul）
  • 虐待のサイン／権利擁護の観点（Noul）
  • 保護者への共有事項（Noul）
  • 本人の状態・記録の具体性（Score）

見てほしいところ

  • 16件 × 6問 が 1秒かからずに終わる
  • しきい値を動かすと
    管理者が読む件数と見逃しが連動する
  • 「今日は楽しそうだった」だけの記録は
    記録の具体性 0（監査対策にも使える）
  • その場で記録を打ち込んで判定

デモ② 問い合わせトリアージ 運営系

Webフォームに届く問い合わせ（ダミー14件）を一括判定

  • サービス：児童発達支援／放デイ／就労移行／定着／その他
  • 送り主：保護者／本人／相談支援専門員・行政／企業
  • 見学希望・受給者証の質問・苦情（Noul）
  • 緊急度（Score）

見てほしいところ

  • confidence のしきい値で
    自動振り分け率 と 自動分の正解率のトレードオフ
  • 曖昧な問い合わせ（お礼だけ、年齢が書いていない等）は confidence が下がって人に回る
  • 質問JSONをその場で書き換えて再実行（例：「SNS経由か？」を追加）

デモ③ AIチャットのガードレール 開発系

就職・就労相談チャットへの入力（ダミー12件）を、LLM に渡す前にチェックする

  • 危機対応（自傷・希死念慮）→ 人につなぐ
  • プロンプトインジェクション
  • 個人情報（氏名・電話・手帳番号）
  • 医療判断の要求（薬の量・診断）
  • 対象内／対象外（Choice）、困り度（Score）

仕事ナビの話をそのまま題材に

  • いま：Haiku で前後チェック → 前後 1秒ずつ
  • Jev：4種類のチェックを1回、数百msで
  • 生成とガードを分ける構成（IEPでも出た案）
  • 「消えてしまいたい」のような遠回しな表現を拾えるか？ → しきい値をどこに置く？

社内で出ている慎重論にどう答えるか

懸念考え方
精度は？ 偽陽性・偽陰性が気になる確率が返るので、しきい値で FP / FN のどちらを許すかを設計できる。
正解付きのサンプルで、デモのようにトレードオフの曲線を描いてから決める
「なぜマッチか」の説明が価値では？2段構成：Jev で速く安く絞り込み・並べ替え → 上位だけ LLM で説明を作る
「ハルシネーションしない」は本当？自由文を出さないだけで、判断を間違えることはある。出力の形式が崩れないことと、判断が正しいことは別
中身がよく分からない（巨大Switch文？）それで十分。if 文の条件を自然言語で書けると思って使う

障害福祉で使うときの注意

  • データ
    • 支援記録は要配慮個人情報の塊。外部API（米国企業）に送る前提で、同意・匿名化・契約・データ保持を確認する
    • 今日のデモはすべてダミー
  • 判断の責任
    • 虐待の疑い・事故報告は法令上の義務。AIは「見落とさないための補助」であって、判定はしない
    • 見逃しと過検知はコストが非対称 → しきい値は安全側に
  • 精度
    • 確率がどれだけ当たっているかは自分たちのデータで検証してから使う
    • 正解ラベル付きのサンプルを少数でも作るのが第一歩
  • 現場の受け止め
    • 「AIに見張られている」ではなく「書いた記録が誰かに届く」体験として設計する

ブレスト：判断を棚卸しする

私たちの事業・プロダクト・サービスの中で、
選ぶ / 点をつける / Yes・Noを決める が
たくさん起きているのはどこ？

① 件数

1日・1か月で何回起きる？
いま誰が（人・仕組み）判断している？

② 間違えたときのコスト

見逃すと何が起きる？
過検知だと何が起きる？

③ 判断材料

テキスト／フォームとして
すでにデータになっている？

観点の例：利用者・家族の体験／支援の質／現場の業務負荷／事業の運営・収益／プロダクトの機能・開発
件数が多く、データがあり、外したときのコストが許容できるもの → まず試す候補

ブレストの種

支援系

  • 連絡帳・支援記録 → 保護者に共有すべき事項の抜け漏れチェック
  • モニタリング記録 → 個別支援計画の目標ごとの達成度スコア
  • 就労移行の日報 → 体調悪化・通所中断のサインを早めに検知
  • 定着支援の面談記録 → 離職リスクのスコア
  • ケース記録 → 加算の算定要件を満たす記載があるか

運営系

  • 問い合わせ・見学申込の振り分け、折り返しの優先度付け
  • 苦情・ヒヤリハット報告の分類と傾向分析
  • 求人応募者の書類一次チェック（※バイアスに注意）
  • 請求前チェック：実績記録と計画の整合性
  • 社内ヘルプデスク・稟議の規程チェック
  • LLMで作った文書の品質ゲート（LLM × Jev）

開発系（社内で既出）：tool call の結果を圧縮する／長い問答を Jev で判定する（grill-jev）／雑で速い Linter／QA の Judge を置き換えてテストコストを下げる

Appendix：デモの動かし方

pip install -r requirements.txt
export TYPESAFE_API_KEY=...            # console.typesafe.ai で発行
python demo/server.py                  # → http://localhost:8000

# キーがない／会場のネットワークが不安定な場合

JEV_OFFLINE=1 python demo/server.py    # 強制的にオフライン
